# Editor shader preparation

The editor shows a compact 640x240 window centered in the primary monitor's work area after Vulkan and the GUI backend are initialized. During initial renderer setup, it presents a loading screen and continues processing window events while shader compilation and pipeline creation run on a worker. This phase has an animated progress bar because its complete task count is not known in advance. When bootstrap completes, the same window switches to the configured editor size and display mode before the editor UI appears.

After the scene loads, preparation prioritizes the collected cameras' rendering modes. Once those pipelines are ready, the scene can be presented while the remaining supported camera modes, debug views and profiling variants prepare in the background. The editor's bottom status bar shows shader progress, asset loading/scanning, and Console warning/error counts. Click the activity or Background button for current shaders, asset names, and failure details; hover the activity for a quick summary. The Background count represents active categories (shader preparation, asset loading, scanning), not individual shaders or assets. Warning/error buttons open the corresponding Console filter. Acknowledge a background failure to return to normal activity status; its details remain accessible in the popup. The bar shows Ready when idle and reserves space below docked panels. Blocking project/scene loading dialogs remain.

Shader counts measure builds, not elapsed time; new scene features or rendering modes can add requests. Up to four preparation builds run at a time by default when hardware permits (see below), allowing shader compilation to overlap driver pipeline creation. Slang work uses isolated global compiler contexts for the configured worker count; the shared Vulkan pipeline cache still serializes driver creation calls. Required builds are scheduled before optional work. Finished pipelines are published by the owning thread before rendering uses them.

The status bar uses the same height as a tab row. Its activity label sits immediately before the progress indicator in the group aligned to the right, followed by background activity and Console controls.

Switching modes promotes the newly required queued builds. Already running compiler or driver builds finish first. Shader source optimization and Vulkan driver compilation can each take significant time on a cold cache; displaying progress does not reduce those individual costs.

`Scripts/install_apps.py` preserves `bin/ShaderBinaries` and `bin/PipelineCache` even when cleaning an installation. Shader dependency keys and Vulkan device/driver identity checks still reject incompatible cached data. `--incremental` retains its existing build behavior. Custom cache locations set through `EVOENGINE_SHADER_CACHE_DIR` and `EVOENGINE_PIPELINE_CACHE_DIR` remain supported.

Compatible Slang sessions reuse imported modules within each compiler context. Compiler options, include paths and global defines must match; changed source or imported dependencies invalidate the session. Each session retains at most eight distinct root shader paths before being recycled. On Windows and Linux, the default is four workers with at least eight logical CPU threads and 30 GiB of OS-visible physical RAM (allowing for reserved memory on nominal 32 GiB machines). Otherwise it is two, or one when the CPU reports only one or two logical threads. Unknown hardware falls back to two. Hardware selection is cached for the process; it does not adjust to changing memory pressure. This threshold is based on the Sponza 1080p sweep, where four workers peaked at 25.79 GiB process commit; other scenes can require more memory.

`EVOENGINE_SHADER_COMPILER_WORKERS` accepts integers 1 through 8 and overrides hardware selection. Set it before launching the application. One selects serial preparation for comparisons or lower memory use. Runtime preparation remains synchronous.
